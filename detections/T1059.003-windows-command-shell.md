# Windows Command Shell (T1059.003)

| | |
|---|---|
| Tactic | Execution (TA0002) |
| Technique | T1059 Command and Scripting Interpreter |
| Sub-technique | T1059.003 Windows Command Shell |
| Data source | Sysmon Event ID 1 (Process Create) |
| Severity | Medium |
| Status | tested |

## What it detects

Execution of commands and scripts through `cmd.exe`, the native Windows command
interpreter. Attackers reach for it because it is present everywhere, it is a trusted
system binary (living off the land, so signature-based AV has nothing to match), it is
logged far less thoroughly than PowerShell, and `/c` runs a command or a `.bat` file and
exits.

## Test case

Atomic Red Team T1059.003, test 1: `powershell` used `Start-Process` to spawn
`cmd.exe /c "...\T1059.003_script.bat"`, a batch file from the `ExternalPayloads`
directory.

## Detection logic

The core of the technique is `cmd` itself, which is mandatory. The parent
(`powershell` via `Start-Process`) is left out: it is an artifact of Atomic Red Team, and
in a real attack the parent could be Word, Excel or an exploit. Anchoring on it would
narrow the rule down to the lab scenario.

The suspicious pattern is `cmd` launching a script file from a non-system directory. That
is three conditions: a path with a drive letter (`X:\`) has to follow `/c`, which rules out
commands such as `cmd /c btool` and `cmd /c whoami`; that path must not be under `Windows`
or `Program Files`; and the path of `cmd` itself at the start of the string must not be
considered, only the argument.

## SPL

```
index="windows_sysmon" EventCode=1 OriginalFileName="Cmd.Exe"
| regex CommandLine="(?i)cmd(\.exe)?\s+/[ck]\s+\"*[A-Z]:\\\\(?!(Windows|Program Files))"
| table _time User Image OriginalFileName ParentImage ParentCommandLine CommandLine
```

The regex piece by piece:

- `(?i)` makes the pattern case insensitive. The `regex` command, unlike the base search,
  is case sensitive by default, so without it `/C`, `c:\temp` and a lowercase `c:\windows`
  in the exclusion all behave differently from their counterparts
- `cmd(\.exe)?\s+/[ck]\s+` is the entry point. The command line records the invocation as
  it was typed, and `cmd /c` without the extension is the common form; `/k` runs a command
  the same way and leaves the shell open
- `\"*` allows zero or more quotes, since a batch invocation really does produce `""C:\...`
- `[A-Z]:` requires a drive letter and colon, which is what rules out `btool` and `whoami`
- `\\\\` is a literal backslash: two for the regex, doubled again because SPL eats half
- `(?!(Windows|Program Files))` is a negative lookahead, so a system folder must not follow `X:\`

The interpreter is identified by `OriginalFileName` rather than by `Image`, for the same
reason as in the certutil rule: `Image` is a path and a renamed `cmd.exe` defeats it.

## Why the simple version did not work

The earlier attempt, `CommandLine!="*C:\\Windows\\*"`, filtered out the batch file itself.
The reason is that `!=` looks for a substring anywhere in the string, with no notion of
position, and the command line contains the full path of `cmd` itself:
`C:\WINDOWS\system32\cmd.exe /c ...`. The filter saw `C:\Windows` in the interpreter path
at the start of the string and discarded the event, even though the script argument came
from an unusual directory.

Excluding a system path with `CommandLine!=` is therefore incompatible with `cmd`, because
`cmd` lives in `C:\Windows`. A regex is required, since it understands position while `=`
and `!=` do not. This is a property of text matching in any SIEM, not of Splunk: matching
without position means simple operators, matching with position means regular expressions.

## Result

The regex matches only the batch files from `ExternalPayloads` and filters out the noise
from the Splunk forwarder (`cmd /c btool ...`) and a mimikatz cradle
(`cmd /c powershell ...`), neither of which has `X:\` after `/c`.

## Known gaps

- The rule is built on a single test (T1059.003-1) and catches one class of scenario.
- `cmd /c whoami & net user` with no file is the same technique and is not caught, since
  there is no path or directory to match. This is a deliberate slice, not an oversight.
- Inline execution has to be caught by different signals: an anomalous parent
  (`winword.exe -> cmd`), patterns of hostile commands (`whoami`, `net user`, `certutil`),
  or a burst of discovery commands in sequence. Those are separate rules.
- One rule cannot cover T1059.003. 

## Gotchas

- A backslash inside a regex inside SPL goes through two layers of escaping. A literal `\`
  becomes `\\` for the regex and `\\\\` in SPL. The error `unknown property after \P` means
  an under-escaped `\P`.
- The `regex` command is case sensitive, the base search is not. Every exclusion written
  without `(?i)` is an evasion: `/C` instead of `/c`, `c:\` instead of `C:\`, and
  `c:\windows\` slipping past an exclusion that only lists `Windows`.
- The command line is recorded as it was invoked, not normalised. `cmd` and `cmd.exe` are
  the same program and two different strings, and a pattern that hardcodes one of them
  misses the other.
- Legitimate software also runs `cmd` from user-writable paths, so false positives are
  expected. That is why the severity is Medium rather than High.

## Alert configuration

Scheduled search, cron `*/5`, time range last 15 minutes, expires after 168 hours,
triggers on more than 0 results, severity Medium.

The window is three times the schedule, so every event is reported three times. Either cut
the window to 5 minutes, or keep the overlap as protection against indexing delay and
enable throttling.

Medium because this is worth a look but is not proof of compromise.

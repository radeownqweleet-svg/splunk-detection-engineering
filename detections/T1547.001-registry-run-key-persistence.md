# Registry Run Key Persistence (T1547.001)

| | |
|---|---|
| Tactic | Persistence (TA0003), Privilege Escalation (TA0004) |
| Technique | T1547.001 Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder |
| Data source | Sysmon Event ID 1 (Process Create), Event ID 13 (Registry Value Set) |
| Severity | Medium |
| Status | tested |

## What it detects

A value written to a Run key survives reboot: everything listed under
`...\CurrentVersion\Run` is started by `explorer.exe` at the next user logon.
There is no scheduler and no trigger logic behind it, which is exactly why
attackers like it. Writing to `HKCU` does not require administrator rights.

This is often confused with Scheduled Tasks. The mechanisms are different, and so is
the telemetry:

| | Run key | Scheduled Task |
|---|---|---|
| Technique | T1547.001 | T1053.005 |
| Started by | `explorer.exe` at logon | the `Schedule` service |
| Parent process | `explorer.exe` | `svchost.exe` |
| Trigger | logon only | time, event, idle, network |
| Rights | user is enough (HKCU) | SYSTEM task needs admin |
| Telemetry | Sysmon 13 | Sysmon 11, Security 4698 |

Autostart lives in more than one place, and a single rule does not cover all of them:

- `HKCU\...\CurrentVersion\Run` and `RunOnce`, writable by the user
- `HKLM\...\CurrentVersion\Run` and `RunOnce`, needs admin, applies to everyone
- the Startup folder, which produces a file event (EID 11), not a registry one
- `Winlogon\Shell` and `Userinit`, which is T1547.004 and replaces an existing value

## Test case

Atomic Red Team T1547.001, test 1:

```
cmd.exe /c REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
        /V "Atomic Red Team" /t REG_SZ /F /D "C:\Path\AtomicRedTeam.exe"
```

## Detection logic

Sysmon Event 1 and Event 13 are correlated by `process_guid`, which is identical for
every event produced by the same process instance.

The rule has two independent branches, because a Run key can be written in two
different ways and the evidence is not the same.

Branch A covers writes made through `reg.exe`:

```
ofn="reg.exe" cl="*CurrentVersion\\Run*" event_code=13
```

`OriginalFileName` only exists on Event 1, and `event_code=13` requires the registry
event, so the condition reads as "reg.exe started against a Run key and actually wrote
something". The value itself is not inspected here. Calling `reg.exe` against autostart
is anomalous on its own.

The parent process is deliberately not part of the condition. Requiring an interpreter
in `ParentImage` was considered and dropped: `ParentImage` is a path on disk, so renaming
the binary defeats it, and Sysmon has no `ParentOriginalFileName` field. The real name of
the parent can only be recovered by pivoting on `ParentProcessGuid` to its own Event 1,
which is a lot of machinery for a signal that is not load-bearing.

Branch B covers writes made without `reg.exe`:

```
event_code=13 target_object IN (...) details IN (...)
```

`New-ItemProperty` and `Set-ItemProperty` write to the registry from the PowerShell
process itself. No `reg.exe` is created, `ofn` is `PowerShell.EXE`, and branch A stays
silent. The only thing left to judge is what was written: `target_object` defines the
area (which key was touched) and `details` provides the trigger (what value landed there).

Suspicious content in `details`: an interpreter or LOLBin (`powershell`, `wscript`,
`cscript`, `mshta`, `rundll32`, `regsvr32`, `msbuild`), a user-writable directory
(`\AppData\`, `\Temp\`, `\Downloads\`, `\Public\`, `\ProgramData\`), a script extension,
or obfuscation markers (`-enc`, `-w hidden`, `FromBase64`, `IEX`).

Paths are matched by listing suspicious locations rather than by excluding
`C:\Windows` and `C:\Program Files`. The inverse filter leaks: a value such as
`rundll32.exe C:\Users\...\Temp\evil.dll,Start` starts with a system path and passes
straight through it. Run keys also legitimately contain unexpanded `%APPDATA%\...`
strings, which the inverse filter flags as suspicious.

Each branch is wrapped in its own parentheses. The `search` command evaluates `OR` before
`AND`, so without them branch B ends up nested inside the conditions of branch A and can
never fire on its own.

## SPL

```
index="windows_sysmon" (EventCode=1 OR EventCode=13)
| stats values(OriginalFileName) as ofn values(EventCode) as event_code values(CommandLine) as cl
        min(_time) as FirstTime max(_time) as MaxTime
        values(TargetObject) as target_object values(Details) as details
        values(Image) as image values(User) as user values(host) as host
        by process_guid
| search ((ofn="reg.exe" cl="*CurrentVersion\\Run*" event_code=13)
      OR (event_code=13
          target_object IN ("*\\Run\\*","*\\RunOnce\\*","*\\Winlogon\\Shell","*\\Winlogon\\Userinit","*\\User Shell Folders\\Startup")
          details IN ("*powershell*","*pwsh*","*cmd.exe*","*wscript*","*cscript*","*mshta*","*rundll32*","*regsvr32*","*msbuild*",
                      "*\\AppData\\*","*\\Temp\\*","*\\Downloads\\*","*\\Public\\*","*\\ProgramData\\*",
                      "*.vbs","*.js","*.bat","*.cmd","*.ps1","*.hta",
                      "*-enc*","*-w hidden*","*FromBase64*","*IEX*")))
```

The `(EventCode=1 OR EventCode=13)` filter sits before the first pipe on purpose. An
earlier rule in this repo groups the whole index first and filters afterwards, which
works in a lab and does not work anywhere else.

`field IN ("a","b")` replaces a chain of `OR`. Wildcards inside `IN` work in the
`search` command but are not expanded in `where`, where `LIKE` is required.

## Event 13 fields

| Field | Contents |
|---|---|
| `TargetObject` | full key path including the value name: `HKU\S-1-5-21-...-1001\Software\Microsoft\Windows\CurrentVersion\Run\Atomic Red Team` |
| `Details` | the value data: `C:\Path\AtomicRedTeam.exe` |
| `Image` | the process that wrote it: `C:\Windows\system32\reg.exe` |
| `EventType` | `SetValue`, `CreateKey`, `DeleteKey` |

## Result

One row, no false positives. `event_code` contains both `1` and `13`, so the two events
were joined on `process_guid`. `ofn` is `reg.exe`, `target_object` holds the Run key with
the value name, and the activity window is 5 milliseconds.

Branch A fired. Branch B stayed silent, which is correct: the atomic writes
`C:\Path\AtomicRedTeam.exe`, an ordinary `.exe` outside user-writable directories, and
it matches none of the content markers.

## Known gaps

- Branch B has never fired. It is written but not validated. Overriding the atomic value
  through `-InputArgs` is the way to exercise it.
- The Startup folder path of this technique produces Event 11 (FileCreate), not Event 13,
  and is not covered here at all. It needs a separate rule.
- Only one atomic test was executed. T1547.001 has at least three classes of
  implementation and this rule was built against one of them.
- `HKLM` Run keys are matched by the `*\\Run\\*` pattern, but that path was never tested.

## Gotchas

- Sysmon does not write `HKCU`. The user hive is expanded to `HKU\<SID>`, even though the
  `reg.exe` command line on screen clearly says `HKCU`. A condition on `HKCU\*` never
  matches anything.
- `Details` does not always show the data. `REG_SZ` appears as a plain string, numeric
  types carry their type (`DWORD (0x00000001)`), and binary values collapse into
  `Binary Data` with no content at all.
- Field names are case sensitive, field values are not. After `values(Details) as details`
  the field `Details` no longer exists, and `search Details IN (...)` silently returns
  nothing. A branch can be dead without a single error on screen.
- A backslash inside double quotes is an escape character. `"*\Winlogon\Shell"` becomes
  `*WinlogonShell` and matches nothing. It has to be doubled.
- Dots do not need escaping. `search` and `IN` use globs, not regular expressions, so a
  dot means a dot. Regex escaping rules only start at `rex`, `regex` and `match()`.
- `values (CommandLine)` with a space before the parenthesis breaks the syntax and is
  almost invisible when reading.
- `AND` and `OR` do not bind the way they do in most languages. The `search` command
  evaluates `NOT`, then `OR`, then `AND`, so `OR` groups more tightly and an unparenthesised
  branch silently absorbs its neighbour. Parenthesise every branch and the question never
  arises.
- One branch can swallow the other. The first version of this rule was
  `(reg.exe AND cl AND 13 AND target_object AND details) OR (13 AND target_object AND details)`.
  The first condition is a strict subset of the second, so `A OR B` where `A ⊂ B` is just
  `B`, and branch A contributed nothing. Branches have to require different things.
- Exact command line spelling is a weak signal. In the log `reg.exe` shows `REG  ADD`
  with two spaces while the parent `cmd.exe` shows one, and a search for
  `CommandLine="*REG ADD*"` found one event out of two. A stray space, a quote, or `/v`
  instead of `-v` is enough to blind the rule.
- `Image` and `ParentImage` are paths on disk and change when the binary is renamed.
  `OriginalFileName` comes from the PE resources, is fixed at compile time, and survives
  renaming. `parent_process_exec` does not help: it is a CIM alias built on top of the same
  `ParentImage`, so it is defeated the same way.

## Alert configuration

Scheduled search, cron `*/5`, time range last 15 minutes, expires after 168 hours,
triggers on more than 0 results, severity Medium.

A 15 minute window on a 5 minute schedule makes every event fire three times. Either
match the window to the schedule, or keep the overlap as protection against indexing
delay and enable throttling on `process_guid`.

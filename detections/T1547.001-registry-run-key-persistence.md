# Registry Run Key Persistence (T1547.001)

| | |
|---|---|
| Tactic | Persistence (TA0003), Privilege Escalation (TA0004) |
| Technique | T1547.001 Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder |
| Data source | Sysmon Event ID 1 (Process Create), Event ID 13 (Registry Value Set) |
| Severity | Medium |
| Status | tested |

## What it detects

This rule detects updates to autostart registry keys, used by attackers to persist on a machine

## Test case

| Atomic Test | What it does | Writes to |
|---|---|---|
| 1 | `reg.exe` writes a value to the user Run key | `HKCU\...\CurrentVersion\Run` |
| 2 | `reg.exe` registers a DLL loaded by `runonce.exe` at logon | `HKLM\...\RunOnceEx\0001\Depend` |
| 3 | `powershell.exe` writes a value that fileless-executes `Discovery.bat` at the next logon | `HKLM\...\RunOnce\NextRun` |
| 9 | `powershell.exe` writes a value that launches a hidden PowerShell script at every logon | `HKU\S-1-5-21...\...\Run\socks5_powershell` |
| 10 | `powershell.exe` repoints the machine-wide Startup folder to a folder it created in Temp, needs admin | `HKLM\...\Explorer\User Shell Folders\Common Startup` |
| 11 | `powershell.exe` repoints the user Startup folder to a folder it created in Temp, so anything dropped there runs at logon | `HKU\S-1-5-21...\...\Explorer\User Shell Folders\Startup` |
| 12 | `powershell.exe` creates the Explorer policy key if missing and writes a value that runs `calc.exe` at logon | `HKU\S-1-5-21...\...\Policies\Explorer\Run\atomictest` |
| 13 | same as 12 but machine-wide, so the value runs for every user that logs on | `HKLM\...\Policies\Explorer\Run\atomictest` |
| 14 | `powershell.exe` backs up the Userinit value, then appends a payload to it so it runs at every logon before the desktop appears | `HKLM\...\Winlogon\Userinit` |
| 15 | `powershell.exe` backs up the Shell value, then appends a payload to it, replacing what Userinit starts as the desktop | `HKLM\...\Winlogon\Shell` |

## Detection logic

Sysmon Event 1 and Event 13 are correlated by `process_guid`, which is identical for
every event produced by the same process instance.

The rule has three branches, because a Run key can be written in different ways and the evidence is not the same. Before dividing into branches, there is a filter based on `TargetObject` field, which drops every registry write outside autostart paths.

Branch A covers writes made through `reg.exe`:

```
ofn="reg.exe" cl="*CurrentVersion\\Run*" event_code=13
```

`OriginalFileName` only exists on Event 1, and `event_code=13` requires the registry
event, so the condition reads as "reg.exe started against a Run key and actually wrote
something". The value itself is not inspected here. Calling `reg.exe` against autostart
is anomalous on its own.

The parent process is deliberately not part of the condition. Requiring an interpreter
in `ParentImage` was considered and dropped: `ParentImage` is a path on disk, so renaming
the binary defeats it, and Sysmon has no `ParentOriginalFileName` field. The real name of
the parent can only be recovered by pivoting on `ParentProcessGuid` to its own Event 1,
which is a lot of machinery for a signal that is not important.

Branch B covers writes made without `reg.exe`:

```
event_code=13 details IN (...)
```

`New-ItemProperty` and `Set-ItemProperty` write to the registry from the PowerShell
process itself. No `reg.exe` is created, `ofn` is `PowerShell.EXE`, and branch A stays
silent. The only thing left to judge is what was written: `details` provides the trigger (what value landed there).

Suspicious content in `details`: an interpreter or LOLBin (`powershell`, `wscript`,
`cscript`, `mshta`, `rundll32`, `regsvr32`, `msbuild`), a user-writable directory
(`\Temp\`, `\Downloads\`, `\Public\`, `\ProgramData\`), a script extension,
or obfuscation markers (`-enc`, `hidden`, `FromBase64`, `IEX`).

Branch C looks for writes made in rare `TargetObjects`:

```
(target_object IN ( "*RunOnceEx\\*","*\\User Shell Folders\\*Startup", "*Policies\\Explorer\\Run*","*\\Winlogon\\Userinit", "*\\Winlogon\\Shell") NOT details="*\\Start Menu\\Programs\\Startup")
```

This branch does not look at the value at all. Nothing legitimate writes to `RunOnceEx`,
to a policy Run key on a workstation, or to `Winlogon` outside of Windows setup, so the
location alone carries the signal.

For two of these keys the value could not carry it anyway. `User Shell Folders` holds a
directory path, not a command, so no interpreter or extension will ever appear in it. And
an attack on `Userinit` and `Shell` appends to the existing value instead of replacing it,
which means a legitimate system path is always present in `details`. Judging these keys by
their content would mean waiting for a signal that never comes.

The `NOT` excludes the default Startup path, which is written back every time an atomic
cleanup runs.


Each branch is wrapped in its own parentheses. The `search` command evaluates `OR` before
`AND`, so without them branch B ends up nested inside the conditions of branch A and can
never fire on its own.

## SPL

```
index="windows_sysmon"
    (EventCode=1
     OR (EventCode=13
         TargetObject IN ("*\\Run\\*", "*\\Run", "*\\RunOnce*",
                          "*\\Winlogon\\Shell", "*\\Winlogon\\Userinit",
                          "*\\User Shell Folders\\*Startup")))
| stats values(OriginalFileName) as ofn
        values(EventCode)        as event_code
        values(CommandLine)      as cl
        min(_time)               as FirstTime
        max(_time)               as MaxTime
        values(TargetObject)     as target_object
        values(Details)          as details
        values(Image)            as image
        values(User)             as user
        values(host)             as host
        by process_guid
| search ((ofn="reg.exe" cl="*CurrentVersion\\Run*" event_code=13)

      OR (event_code=13
          details IN ("*powershell*", "*pwsh*", "*cmd.exe*", "*wscript*", "*cscript*",
                      "*mshta*", "*rundll32*", "*regsvr32*", "*msbuild*",
                      "*\\Temp\\*", "*\\Downloads\\*", "*\\Public\\*", "*\\ProgramData\\*",
                      "*.vbs", "*.js", "*.bat", "*.cmd", "*.ps1", "*.hta",
                      "*-enc*", "*hidden*", "*FromBase64*", "*IEX*"))

      OR (target_object IN ("*RunOnceEx\\*", "*\\User Shell Folders\\*Startup",
                            "*Policies\\Explorer\\Run*",
                            "*\\Winlogon\\Userinit", "*\\Winlogon\\Shell")
          NOT details="*\\Start Menu\\Programs\\Startup"))
| `ctime(FirstTime)`
| `ctime(MaxTime)`
```

The path filter sits before the first pipe on purpose. An earlier rule in this repo
groups the whole index first and filters afterwards, which works in a lab and does not
work anywhere else.

`field IN ("a","b")` replaces a chain of `OR`. Wildcards inside `IN` work in the
`search` command but are not expanded in `where`, where `LIKE` is required.

## Result

The rule fires on 10 of the 20 atomic tests. All 10 were run and confirmed in Splunk.

Branch A catches tests 1 and 2. Branch B catches tests 3, 9, 10 and 11. Branch C catches
tests 2, 10, 11, 12, 13, 14 and 15.

The branches overlap. Tests 12, 13, 14 and 15 are caught by branch C alone, and nothing
else would find them.

The other 10 were not run. They write somewhere the rule does not look. Tests 4, 5, 6
and 7 drop a file into the Startup folder, which is Event 11, not Event 13. Tests 8 and
20 write to `Software\Classes\...\shell\command`. Test 16 uses `secedit`. Tests 17, 18 and 19 write
to `BootExecute`, RDP startup programs and `BootVerificationProgram`. None of these paths
are in the rule.

Test 10 did not produce an event at first. The registry write worked, but the Sysmon
config did not watch `Explorer\User Shell Folders`, so nothing was logged. Added a
`TargetObject` rule for that path to the config, reloaded it, and the event appeared.

## Known gaps

- The Startup folder path of this technique produces Event 11 (FileCreate), not Event 13,
  and is not covered here at all. It needs a separate rule.
- `details` is still judged after `stats`, on the bag of values from the whole process.
  A process that writes a harmless value to one autostart key and a suspicious value to
  another matches branch B even though no single event does. The base filter cut the scale
  of this down to autostart writes only, but it did not remove it.
- The list of autostart paths exists twice, in the base filter and in branch C. Adding a
  key to one and not the other goes silently wrong in either direction.
- `"*\\Run"` in the base filter never matches. Event 13 always carries the value name, so
  the path never ends at the key. It would only matter with Event 12.
- The `NOT` is asymmetric. Restoring the default Startup folder is excluded, restoring the
  default `Winlogon` value is not.
- No baseline. One endpoint, no real software, no measured false positive rate.

## Sysmon config

The stock SwiftOnSecurity config does not watch the `HKLM` copy of
`Explorer\User Shell Folders`, so test 10 produces no telemetry at all. The `HKCU` copy
used by test 11 is logged without any change. Add the path to the `RegistryEvent` include
group and reload the config:

```xml
<TargetObject name="T1547.001,UserShellFolders" condition="contains">Explorer\User Shell Folders</TargetObject>
```

```
sysmon -c <path-to-config>.xml
```

## Alert configuration

Scheduled search, cron `*/5`, time range last 15 minutes, expires after 168 hours,
triggers on more than 0 results, severity Medium.

A 15 minute window on a 5 minute schedule makes every event fire three times. Either
match the window to the schedule, or keep the overlap as protection against indexing
delay and enable throttling on `process_guid`.
